14. Final category/product/service catalogue (same — schema-only).
15. ~~Guest checkout vs. login-required~~ — **RESOLVED by final client decision**: guest browsing is allowed, guest add-to-cart is allowed (client-local cart, unchanged from today's `CartProvider`/`localStorage` behavior), but guest **order placement is NOT allowed** — the customer must authenticate before checkout. Flow: Browse → Add to Cart → Cart → Customer Login/Signup → Checkout → Place Order. Consequently `orders.customer_id` is `NOT NULL` (`PHASE_2_BACKEND_DATABASE_SCHEMA.md` §7/§13), the server-persisted `carts`/`cart_items` tables exist only for an authenticated customer — Design A (hybrid) from `PHASE_2_BACKEND_DATABASE_SCHEMA.md` §12, with the anonymous cart staying client-local and merging into the server cart at login — and `POST /orders` is Customer-only (never public); `GET /orders/:id` is Customer + ownership (`PHASE_2_BACKEND_API_CONTRACT.md`). Already implemented in Phase 3.
16. ~~Multi-city cart behavior~~ (`PHASE_2_BACKEND_DATABASE_SCHEMA.md` §12 — `cart_items.city_id` is structural only) — **RESOLVED by final client decision**: this structural design is final, not merely a placeholder pending a restriction. The cart may contain items spanning multiple cities; each cart item carries and is priced/offer-resolved against its own `city_id`; there is no global cart-wide single-city restriction, and none should be invented. Order creation independently validates each line item against its own selected city and that city's current service availability.
17. ~~`Offer` vs. `Service.offerPrice` stacking precedence~~ — **RESOLVED by the Phase 3 Offer/pricing correction**: they now combine. An Offer is either `ALL_INDIA` (nationwide) or `CITY` (one named city); a `CITY` offer always takes priority over a matching `ALL_INDIA` offer for the same service/city (never both, never stacked); the resulting single offer discount is applied on top of `Service.offerPrice` and combined with the service's own `mrp`-vs-`offerPrice` discount into one total. See `PHASE_2_BACKEND_DATABASE_SCHEMA.md` §10 (now updated) and `PHASE_3_BACKEND_IMPLEMENTATION.md` §8 for the full rule and implementation.

Deployment path: ECR → ECS Fargate → ALB → RDS, as already designed in `PHASE_2_BACKEND_SYSTEM_ARCHITECTURE.md` §2 and `PHASE_2_AWS_ARCHITECTURE.md`.
20. ~~Whether Admin's scope extends to the existing marketing/content entities~~ (`PHASE_2_BACKEND_DATABASE_SCHEMA.md` §6 content-tables note, `PHASE_2_BACKEND_API_CONTRACT.md` Admin content endpoints) — **RESOLVED by final client decision**: Admin manages ALL business/content fields the platform needs — cities, categories, products, service types, services, service pricing, offers, city availability, listing approval, testimonials, FAQs, homepage sections, headings, descriptions, contact information, navigation, branding, logo, brand assets, promotional content, and other editable business/content fields. Not limited to catalog/pricing/listing-approval. Already implemented in Phase 3 (§12 of `PHASE_3_BACKEND_IMPLEMENTATION.md`).
21. ~~Whether an Admin-authored listing publishes immediately (skips its own approval step)~~ (`PHASE_2_BACKEND_DATABASE_SCHEMA.md` §9) — **RESOLVED by final client decision, and the prior "publishes immediately" assumption was INCORRECT**: there is no fourth role and no second approver. Both Admin-created and Provider-created listings go through the exact same approval pipeline — every listing is created `pending_approval` and must pass through the one shared Admin approval queue before it is publicly visible. Admin is intentionally permitted to approve an Admin-created listing from that same queue (self-approval) — this is a deliberate business rule, not a bug, and no Super Admin / second-approver role is to be introduced. Already implemented correctly in Phase 3 (`createService()` is the one function both `POST /provider/listings` and `POST /admin/services` call; see `PHASE_3_BACKEND_IMPLEMENTATION.md` §9 and `approval.test.ts`).
22. S3 media access pattern — public-read behind CloudFront (this phase's recommendation) vs. signed/restricted delivery (`PHASE_2_AWS_ARCHITECTURE.md` §15).
23. DNS approach for the API subdomain — GoDaddy `CNAME` to the ALB (recommended) vs. delegating the zone to Route 53 (`PHASE_2_AWS_ARCHITECTURE.md` §23).
24. RDS Multi-AZ / backup-retention timing — *when*, not whether, to enable these; both are configuration changes to the existing instance, explicitly out of scope for this design phase (`PHASE_2_BACKEND_SYSTEM_ARCHITECTURE.md` §22).
25. Dev/staging environment strategy and its cost/budget tolerance — separate RDS instance vs. shared-instance-separate-schema, separate vs. shared S3 bucket (`PHASE_2_BACKEND_SYSTEM_ARCHITECTURE.md` §24).
26. MFA requirement for Admin/Provider accounts — recommended in this phase, not confirmed (`PHASE_2_AUTHORIZATION_MATRIX.md` §4).
27. Editing policy for an **already-approved** listing — does a Provider edit to an approved listing re-queue it for approval, or apply immediately? (`PHASE_2_BACKEND_API_CONTRACT.md` Provider section note.) **Still genuinely open as a confirmed business policy; not resolved by the Phase 3 Offer/Pricing correction.** Phase 3 already implements the re-queue behavior as its working default — a Provider's edit to their own approved listing forces it back to `pending_approval`, and a Provider can never publish an edit directly (`PHASE_3_BACKEND_TEST_REPORT.md`, `approval.test.ts`) — but this remains flagged in the Phase 3 documentation as awaiting explicit client confirmation, not a final sign-off. Do not treat this item as resolved and do not change the implemented behavior without that confirmation.

## 3. Assumptions made purely to keep this design internally consistent (flagged, not hidden)

These are not requirements — they are the minimum working assumptions this phase had to make somewhere in the design so the schema/API/auth model would be internally consistent, each cross-referenced to where it's used and explicitly reversible:

- ~~**Cart hybrid design (Design A)** is the recommended default, gated entirely on item 15 above resolving to "guest checkout allowed."~~ — **RESOLVED**: item 15 resolved to guest browsing/add-to-cart allowed, login required at checkout. Design A (hybrid) is now the final architecture, not merely a gated recommendation; Design B is superseded and will not be built.
- ~~**Admin-authored listings publish immediately** (item 21)~~ — **This assumption was INCORRECT and is superseded.** The final decision (item 21 above) is that an Admin-created listing follows the exact same `pending_approval` → shared approval queue → Admin-approves pipeline as a Provider-created listing; it does not publish immediately or skip approval. Admin self-approval from that shared queue is permitted by design.
- **One Cognito User Pool with Groups**, not per-role pools — this is Phase 1's own recommended direction, restated and detailed here, not a new assumption, but still requires the client's explicit sign-off since the brief asks that this "be documented and justified," not merely carried forward.
